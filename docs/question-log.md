# Question Log

更新日期：2026-08-06

## 已处理

### 1. 公开站错误暴露内部登录入口

- 现象
  公开导航仍显示“内部登录”，与“公开站不承载内部审核入口”的目标不一致。
- 影响
  用户会误以为公开站仍保留内部处理流程，且会点击到本不应暴露在公网导航中的路径语义。
- 本次处理
  已从公开导航和移动端抽屉中移除 `login.html` 入口；内部页面仍保留本地工作台访问能力，但不再由公开站主动引流。
- 后续问题
  是否需要把 `login.html`、`desk.html`、`review.html` 的命名进一步迁移到更明确的内部前缀，以减少误解。

### 2. 首页“最新情报”停留在旧时间点

- 现象
  首页决策摘要显示的最新动态落在 2026-07-07，未反映 2026-07-20、2026-07-27、2026-08-03 等后续正式事件。
- 影响
  用户会误判站点没有继续更新，即使正式数据集实际已扩充。
- 本次处理
  重新生成 `data/daily-briefing.json`，使首页摘要重新从最新正式事件、重点试验与质量快照中取数。
- 后续问题
  是否要把首页摘要改成“发布时自动生成且缺失时自动回退到 `events.json` 最近记录”，避免单个 briefing 文件过期导致首页失真。

## 待完善

### 3. GitHub Pages 仍是一个会造成混淆的旧镜像

- 现象
  文档已明确 Cloudflare Pages 才是生产部署，但仓库仍保留 GitHub Pages 配置。2026-08-06 针对提交 `c48b923` 的 Pages 构建失败，而 2026-08-04 的旧 Pages 版本仍可能被访问。
- 影响
  用户可能打开旧的 GitHub Pages 地址，从而看到与 Cloudflare 生产站不一致的页面和数据。
- 当前判断
  这是发布链路治理问题，不应再把 GitHub Pages 当成生产入口。
- 建议后续动作
  1. 明确记录 Cloudflare 生产域名并放入仓库文档。
  2. 在确认 Cloudflare 生产域名稳定后，关闭 GitHub Pages 或将其改为明确跳转页。
  3. 把“生产 URL 核验”加入发布清单，而不是只核对 GitHub 合并状态。

### 4. 首页摘要与正式数据集之间缺少自动一致性保障

- 现象
  `feed.json`、`events.json`、`trials.json` 已更新时，`daily-briefing.json` 仍可能停留在较早时间点。
- 影响
  站点首页会比详情页、专题页和数据集本身更旧。
- 建议后续动作
  1. 将 `npm run briefing:daily` 纳入所有正式发布前的必跑步骤。
  2. 为首页增加“摘要时间早于正式数据更新时间”提示。
  3. 为 `daily-briefing.json` 增加审计项，检测摘要是否落后于 `events.json` 的最新外部事件。
