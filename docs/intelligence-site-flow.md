# 情报网站当前流程与前后台职责

更新日期：2026-08-04

## 1. 当前流程

1. 自动发现  
   来源包括 PubMed、ClinicalTrials.gov、CDE 中国药物临床试验登记平台、重点企业官网与监管入口。脚本只负责抓取、去重、初筛与生成候选，不直接把线索写入正式数据集。

2. 候选分流  
   研究文献与官网更新进入候选池后，再按纳入规则判断是否进入候选处理台。临床试验保留为“试验登记”线索，进入候选池展示，但不进入处理台逐条处置。

3. 候选处理  
   候选处理台只处理两类对象：
   - 研究文献
   - 官网更新

   处理动作只有三种：
   - 确认并完成
   - 保存修改并完成
   - 排除

   每次处理都写入可追溯记录，保留处理人、时间、理由与字段修正结果。

4. 正式收录  
   只有完成来源确认并形成明确处置结果的对象，才进入正式数据集、关系网络、专题聚合、时间线和详情页。

5. 审计发布  
   每次本地启动与发布前，统一执行数据审计，检查结构完整性、交叉引用、来源登记、来源确认时效与内部页面资源。

## 2. 前台页面分工

- `index.html`
  展示正式收录后的总体概览与每日重点，不展示未处理候选作为既成事实。

- `candidates.html`
  展示自动发现后的候选池，包括试验登记线索、研究文献与官网变化线索。

- `desk.html`
  作为内部候选处理台，承接研究文献与官网更新的人工处置闭环。`review.html` 仅保留兼容跳转。

- `radar.html`
  展示官网监测覆盖、变化信号与待继续跟进项。页面强调“变化信号 ≠ 正式结论”。

- `detail.html`
  展示正式数据对象的结构化档案、来源状态、关联关系与最近动态。

- `quality.html`
  展示来源确认覆盖、审计告警、来源登记与复核周期，不把内部判断伪装成外部事实。

## 3. 后台接口职责

- `GET /api/candidate-desk`
  返回处理台队列、筛选结果与已处理状态。

- `POST /api/decisions/:id`
  写入单条候选的处置结果。

- `POST /api/decisions/batch`
  写入批量确认或批量排除结果。

- 兼容路径
  - `GET /api/review-queue`
  - `POST /api/reviews/:id`
  - `POST /api/reviews/batch`

  这些旧路径仍可用，但只作为兼容层，不再作为主命名。

## 4. 数据语义边界

- `待处理`
  代表候选已进入处理台，但尚未形成闭环处置。

- `试验登记`
  代表临床试验作为登记线索保留，不进入处理台逐条确认。

- `已收录`
  代表对象已进入正式数据集。

- `来源已确认`
  代表字段已完成一手来源逐字段确认。

## 5. 本次架构调整

- 对外入口从 `review.html` 切换为 `desk.html`。
- 登录默认跳转改为候选处理台。
- 服务端新增 `candidate-desk` / `decisions` 主路径，并保留旧路径兼容。
- 官网雷达、详情页、首页摘要、质量页统一改用“处理/跟进/收录/来源确认”语义。
- CDE 说明同步改为“试验登记线索”语义，不再描述为 Hermes 审核队列。

## 6. 后续建议

- 如需彻底消除历史命名，可在下一轮把 `data/review-decisions.json` 等内部文件名迁移到 `decision-log.json`，并补一次数据迁移脚本。
- 若后续继续扩展自动化处理，可把“候选处理台”与“正式发布流水线”拆成两个独立状态机，降低候选层和正式层的耦合。
